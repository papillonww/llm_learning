# 转型项目：营销规则理解与优惠计算

状态：默认候选，尚未执行；第 1 周检查可行性，第 5 周前确定数据与基线。面向约 1.5 年营销算法经历，把领域理解转化为可验证的 LLM 训练、评估和工具协作经验。

## 研究问题

输入一段营销规则、订单/商品属性和候选优惠，模型能否抽取条件、判断适用性、选择正确优惠并输出准确到手价？SFT、偏好优化或 GRPO 能改善哪些能力，代价和失败是什么？

先限定单币种、单件订单、至多使用一张优惠券，明确门槛、折扣上限、不适用条件和同价 tie-break。使用公开或自建合成规则，不依赖公司数据。本轮离线正确率不代表线上 GMV、核销或因果 uplift。

## 数据和真值先行

1. 自己定义小型规则 DSL/结构化 schema，再用确定性计算器生成可验证答案；金额用整数最小货币单位或 Decimal，明确舍入顺序。
2. 将结构化规则改写成自然语言，人工核对含义是否保持；记录模板/生成模型、筛选与错误修订。
3. 输出 schema 包括适用候选、最终选择、到手价和对应规则 ID；“满足条件”与“最终选中”分别评估。
4. 初期准备约 20 条开发样本，检查评分器；再扩到数百/千条训练量级，按模板家族、规则组合和实体分组划分。
5. 覆盖边界：刚好门槛、差一单位、封顶、无券可用、多个优惠同价、缺字段、排除条件和无效输入。
6. 最终测试含未见表达与规则组合；不能用最终题目生成训练/偏好数据或调 reward。真值计算器先有独立手算案例核对。

模型输出可以是短 JSON，不要求展示长链推理。新增条件必须有输入依据；缺少必要字段时按 schema 返回需要补充的信息。

## 基线决定 LLM 的作用在哪里

| 条件 | 目的 |
| --- | --- |
| 结构化规则 + 确定性计算器 | 校验标签与计算上限；输入已结构化，不能与自然语言任务直接等价比较 |
| 原模型直接生成 + 固定提示 | 自然语言任务的共同基线 |
| 原模型抽取规则 + 同一计算器工具 | 检查计算能否交给工具，分离理解与算术错误 |
| 同基座 LoRA SFT | 学习规则理解与结构化输出 |
| 同 SFT 起点 + DPO 或 GRPO | 选择一种作为项目主要优化方法，另一种可保留学习实验 |

选 DPO 时，用可核验的正确/错误或条件遗漏对构造偏好，说明这是任务正确性偏好，并不代表真实用户偏好。选 GRPO 时先检查模型同题多次生成是否有奖励差异，避免全错/全对导致无优势。第 8–10 周的通用 RL 练习可直接复用部分任务，按基线难度决定。

## 评估与消融

- 独立报告：格式合法、条件抽取、候选适用性、最终选择、金额精确匹配、缺字段处理。
- 质量检查：规则依据是否真实存在，是否遗漏排除条件或捏造优惠；自动评分外人工看至少 20 条异常。
- 泛化：未见模板、规则组合、边界金额；同时保留原模型确实能做的小型无关任务集。
- 成本：训练 token/耗时、采样数、推理长度、延迟、显存；工具调用开销单独计。
- 主消融只选一个：如去掉边界样本、降低数据质量、去掉一种 reward 信号。其他变量固定，记录预算差异。
- 方案只在 dev 选择，冻结后跑最终测试；接近差异做重复种子或报告区间和局限。

如果简单提示 + 工具已经解决问题，训练收益有限本身也是有效结论；要解释部署复杂度和维护成本，而非强行追求训练后高分。

## 项目节奏

- 第 1–2 周：问题定义、schema、少量手算案例与数据候选。
- 第 3–5 周：真值计算器、数据构建、去重/划分、原模型与工具基线。
- 第 6–7 周：SFT 和 DPO 学习实验积累到项目。
- 第 8–10 周：可行时使用同类短答案任务练 GRPO，先独立核查 reward。
- 第 11 周：锁定主要方法、补齐共同基线和对照。
- 第 12 周：消融、泛化、失败分析，冻结后跑最终测试。
- 第 13 周：复验与报告；有余力再增加工具调用/蒸馏扩展。
- 第 14 周：部署和项目讲述。
